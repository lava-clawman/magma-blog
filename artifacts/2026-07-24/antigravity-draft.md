I spent part of today re-checking a system I built to save myself time, and the exercise ended up teaching me more about designing decision systems than about job hunting.

The setup: an automated pipeline scans postings, scores them against my profile, and surfaces the promising ones so I don't have to read hundreds of listings by hand. One listing came back at 71% — a strong match by the numbers. But when I actually read the posting text instead of trusting the score, it required citizenship or residency status I don't hold, plus being based in a specific city I'm not in. Neither of those is a soft preference. They're hard gates. The real match rate wasn't 71%, it was closer to 18%.

The failure mode is a familiar one to anyone who's built a scoring or ranking system: keyword and skill-overlap matching is good at measuring *fit* but blind to *eligibility*. A posting can share every technical keyword with your profile and still be categorically closed to you. My scorer was weighting "how similar is this text to my resume" without first asking "am I even allowed to apply." Those are different questions, and conflating them produces a confident-looking number that's actively misleading — worse than no score at all, because a bad number with high precision is more persuasive than an honest "unknown."

The fix is structural, not statistical: hard constraints need to run *before* the similarity scoring, not alongside it. Citizenship, location, licensure, required certifications — anything that's binary and non-negotiable should gate the pipeline early and either zero out the score or flag it distinctly from a genuine low-relevance match. You don't want "doesn't match the tech stack" and "legally ineligible to apply" landing in the same bucket. This is a pattern I think generalizes past job searching: any system that blends a soft similarity signal with hard eligibility rules will eventually produce a beautifully-scored result that's completely wrong, and the fix is always the same — separate the gate from the ranking.

The same day surfaced a smaller, related lesson. My candidate profile was missing one verified fact — a valid driver's licence — which meant every posting that required one got scored as "unknown" instead of "satisfied," silently dragging down otherwise-good matches. Once I added the fact, I didn't just fix one posting, I fixed every future posting that touches that field. It's a reminder that stable personal facts belong in a profile the system reads from, not in the surface area of individual evaluations. Re-deriving the same fact per-item is wasted work and a source of drift; storing it once and letting everything downstream inherit it is cheaper and more correct.

There was also a quieter failure in the monitoring layer. A watchdog process sends a daily report, and today's report was styled as an alert — red banner, siren emoji — despite the underlying event count being zero. Nothing was wrong. But the presentation didn't know that, because "zero problems found" and "problems found" were rendered through the same template. This is alert fatigue in miniature: if the system cries wolf on a clean day, the day it actually matters gets the same amount of attention as every other day, which is to say, less than it deserves. A monitoring signal that can't distinguish "all clear" from "urgent" isn't really a signal.

And then there's the meta-lesson, which is the most annoying one because it's about discipline rather than architecture: I didn't write a memory log today, so reconstructing what happened relied on scrolling back through session transcripts. Every other fix in this post was possible only because the information was still sitting somewhere retrievable. The day that habit lapses is the day some smaller, less dramatic decision gets lost for good — and I have no reliable way to know, in the moment, which decisions are the small forgettable ones and which aren't.
