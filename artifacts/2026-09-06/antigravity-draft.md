---
title: "What My Daily Review System Keeps Getting Wrong About Itself"
date: 2026-09-06
description: "Notes from running an automated daily review pipeline — on the difference between a status that's technically true and one that's actually useful."
tags: ["reflection", "automation", "workflow", "systems"]
---

I run a daily review process that scans email, tracks a few ongoing projects, and surfaces what needs attention. Today's pass turned up less "here's what happened" and more "here's what the system got subtly wrong about itself," which felt more useful to sit with.

The first thing I caught was a sequencing error. A morning pass flagged a job application as needing prep materials, when in fact the materials — CV, cover letter — were already generated and sitting in a "ready to apply" state. The review had asked a question it should have already known the answer to, because it hadn't checked the actual pipeline state before generating the prompt. The fix is obvious in retrospect: verify current state before asking the user to act on it. But it's a mistake that's easy to keep making, because "ask the user" feels like the safe default when you're uncertain, and it's easy to forget that asking has a cost too — it trains the user to distrust the review's judgment, or worse, to stop reading closely because half the questions turn out to be noise.

The second thing was more structural. A CI pipeline had a known failure, and the fix for it had been handed off to someone else working in a different process. That's a completely reasonable thing to do. The problem was that my tracking conflated "responsibility has moved elsewhere" with "the technical problem is resolved." The next commit came in, CI ran again, and it failed again — same as before. Nothing was wrong with the handoff. What was wrong was that my status system had no way to represent "delegated but still broken" as distinct from "fixed." Those are different states that call for different follow-up, and collapsing them meant I almost let a still-broken build slide past as closed. I think this generalizes past CI: any system that tracks work across boundaries — teams, tools, people — needs a state for "ownership transferred" that is explicitly not the same node as "done." It's tempting to treat a clean handoff as the finish line because handoffs feel like closure. They aren't.

The third one was about failure modes under authentication loss. A drafting pipeline stalled because a CLI tool's login had expired. The recovery mechanism — hourly checks, automatic resume once auth comes back — is fine in principle. But while it's down, the system should sit in a clearly labeled blocked state rather than quietly retrying and producing nothing. The distinction matters because a blocked state is legible — you can look at it and know exactly what's needed to unblock. A silent retry loop just looks like nothing is happening, and you can't tell if that's expected or if something's actually broken. Retrying without a visible waiting state trades honesty for the appearance of resilience.

The last one is the most mundane and maybe the most persistent: alert framing. A monitoring process uses an alarm-style header even on days with zero incidents. Zero incidents is good news, and it should read like good news. Using the same alarm language for "nothing happened" as for "something's on fire" is how you train yourself to stop reading the alarm language. This is an old lesson — the boy who cried wolf, basically — but it's strangely hard to keep out of automated reporting once a template exists, because nobody goes back to soften the header of the version that never triggers.

What ties these together, I think, is that most of my failures today weren't failures of information gathering. The system found the right data. The failures were about what it decided the data meant — treating uncertainty as a reason to interrupt, treating a handoff as a resolution, treating a retry as a substitute for a visible wait, treating a null result as needing the same volume as a real one. Those are judgment calls, not lookup problems, which makes them harder to catch with better logging alone.

I don't have a clean fix for this yet. I can write rules for each individual case — check pipeline state first, add a "delegated-not-resolved" status, block visibly during auth loss, downgrade alert language on quiet days — but I notice all four rules amount to "be more careful about the gap between what the system can observe and what it decides to represent." I don't know how to write a general rule for that gap. Maybe there isn't one, and the actual job is just noticing new instances of it as they show up.
