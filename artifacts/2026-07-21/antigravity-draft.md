title: "What a Stalled Cron Job Taught Me About Asking for Permission"
date: 2026-07-21
description: "Notes from a day of job-search tooling, a context-window blowout, and a stuck system process — on when to push through and when to stop and escalate."
tags: ["reflection", "workflow", "engineering-judgment", "automation"]
---

I spent part of today widening the scope of a job-search tool I've been building — adding CMS and website-builder platforms to the list of roles it searches and scores. It's a small change on paper: a few more keywords, a few more scoring rules, tests passing. But the interesting part wasn't the code. It was everything around the code that either worked cleanly or didn't.

**The honest-signal problem.** I also drafted application materials for a role that sits at the intersection of data engineering and "help the business use AI." The temptation with a hybrid role like that is to stretch your experience to cover every keyword in the posting — I've used one cloud platform a little, so why not imply more? I didn't, and I think that's the right default: lean on the skills you actually have (in this case, two cloud platforms and coursework, not three cloud platforms and production experience) and let the transferable-skills argument do the work instead of quietly inflating a resume line. It's slower and less flattering in the moment. It's also the version that survives a follow-up question in an interview.

**Verify state before acting on it.** While chasing down an old job posting, I matched it against a stale record and almost moved to re-engage before realizing the listing had been archived months ago. The failure mode here is generic and shows up constantly: pattern-matching against history is a search strategy, not a verification strategy. Before I act on any historical record — a job posting, a cached status, an old note — the record needs an independent check against the current live source, not just internal consistency with what I already have on file. This applies well beyond job hunting; it's the same reason "we saw this pass in CI last week" is not the same claim as "this passes now."

**Tooling that hangs at startup is a signal, not a nuisance.** Generating those application materials, my coding assistant stalled during MCP initialization — some project-level tool tried to spin up and never returned. I killed it and reran with the extraneous integrations disabled, which worked immediately. The lesson I want to keep is upstream of that fix: before kicking off a task that doesn't need the full tool surface, do a minimal or non-interactive startup pass. Every optional integration is a dependency that can hang, and "turn off what you don't need" is cheaper done in advance than diagnosed after the fact.

**Big tool outputs need to leave the conversation, not just get summarized.** Separately, I found the root cause of an old dead session: a long run had piled up tool results until the context window blew past its limit, and neither automatic compression nor three recovery attempts could bring it back. Nothing was lost — the underlying records were still on disk — but the live session was unrecoverable. The fix isn't "compress harder," it's architectural: multi-step, high-output work should get split into sub-sessions early, with large results written to files and only summaries kept in the working context. Compression is a patch for a session that's already too full; the actual fix is not filling it up in the first place.

**The hardest call of the day was the one where I did nothing.** A routine cleanup task — fixing a path and removing two outdated scheduled jobs — turned out to be blocked by a system process that hangs on any write, even a no-op rewrite of its existing config. Reading still works; writing doesn't. It would have been easy to route around that at a lower level. I chose to leave the configuration untouched, confirm nothing was corrupted, and wait for a proper administrative session to diagnose the write path directly. That's the boring, correct answer, and boring-and-correct doesn't always feel like progress in the moment. Deferring isn't the same as ignoring, but I notice I have to actively remind myself of that distinction — otherwise "wait for permission" quietly turns into "forget about it."

None of these were dramatic failures. They were small moments where the fast path and the correct path diverged slightly, and the gap only shows up if you're paying attention. What I haven't resolved is how to build that attention into the process itself rather than relying on catching it in the moment — because today I caught it, but I don't have a system that guarantees I will next time.
