## 决策与变更
- 对 [[阳绵优汇]] 的修复形成了明确判断：
  - 不是简单补背景，而是要区分“背景延续”“分隔线延续”“内容区与备案区的视觉边界”。
  - 最终有效方案不是把竖线延伸到备案行，而是把补丁限制在 app 内容区底部交界处。
- 形成了一个更清晰的 [[主动知识库]] 判断框架，可直接服务 [[FlashNotes]] 后续建设：
  - 知识系统的价值在于任务开始前主动激活上下文，而不是被动存储。
  - 研究流程应采用“两段式”：先定义真问题 / problem pack，再引入外部证据生成正式报告。
  - 证据层级应优先保护本机主线事实与旧判断，避免高熵外部输入劫持主题。
  - “生成成功不等于任务完成”，必须有 [[Delivery Guard]] / 结构校验 / 发送回执 / 失败通知。
- 对本地部署模型给出了可执行分档：
  - [[32B 模型]] 是现实主力档，适合内部报告、长文归纳、多文档整理。
  - [[70B 模型]] 属于高配方案，硬件、功耗、运维复杂度显著上升，不应在流程未理顺前优先采用。
  - 对该类政企场景，优先建设文档解析、索引、引用机制与人工复核链路，比盲目追求大模型更重要。

## 错误与改进
- [[阳绵优汇]] 的 UI 修复过程中，前两轮判断只抓到了“背景未到底”和“边线未到底”的表象，第三轮才被用户明确指出真正问题是“交界处缺一小截”，说明视觉问题应尽早以“具体缺口位置”而不是“整体感觉”建模。
- 一度把分隔线直接画入备案号区域，造成“修复有效但视觉更怪”的副作用；后续修正为仅在内容区边缘补线。这是一次典型的“局部有效、整体不对”的 UI 修复教训。
- 对 [[本地 AI 报告系统]] 的建议进一步沉淀为可复用原则：
  - 不先做聊天机器人，先做“证据驱动的报告生成器”。
  - 不把“能启动模型”误判为“能生产”。
  - 不把“模型更大”误判为“准确性自然更高”。
